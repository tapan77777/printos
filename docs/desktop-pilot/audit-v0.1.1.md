# PrintOS Desktop 0.1.1: first Windows pilot audit

Reviewed 26 October 2026 against checkout `a13c2b3`. This is an audit and proposal, not implementation or release approval. The operator registers and onboards shops on the website; an already-onboarded owner should do routine work inside Desktop.

## Decision and scope

**Suitable for an assisted installation/UI assessment; not cleared for a real printing pilot or unattended daily operation.** Resolve the P0 items below and complete the Windows checklist before considering a printing pilot. This audit neither enables customer ordering nor activates a device or worker.

Desktop is a privileged local shell around the hosted owner dashboard, not an offline replacement for that website. Embedded dashboard/API changes can affect installed Desktop independently of its EXE version. The reviewed web source includes the unpromoted onboarding release; its presence in the checkout is not proof it is serving the production domain. No production requests, authenticated data reads, database writes or deployment operations were performed in this audit.

The existing Windows installer remains version 0.1.1, 112,375,279 bytes, built 24 October 2026 around 11:23 IST. SHA-256: `2b75570fedeb7472b5898c64855b117322c578445f6865381ec1b25c427aef85`. Prior extraction verified its current desktop/agent payload. No installer was rebuilt or published here. The installer is unsigned; actual installation and physical output remain unverified.

## Evidence and limits

- Re-ran Desktop's 24 tests and the agent's 81 tests: **105 passed**, no skipped tests. Both typechecks passed. These include injected spooler/cloud behavior, not execution of Windows drivers or PowerShell on Windows.
- Ran the real Electron shell twice against a loopback-only synthetic server, with a fresh temporary profile and a test AES protector injected by the privileged test driver. Confirmed encrypted device identity survives application restart, retains its device scope and does not redeem or create another pairing. Processing remains disabled after restart. This does **not** verify Windows DPAPI, a real owner's cookie, or production enrollment.
- Confirmed the test's user-data/session-data/partition directories use the same temporary profile on both launches.
- A synthetic persistent cloud cookie existed before restart but was absent after restart, despite flushing the cookie store. **Login persistence is unresolved**, and no production cause is inferred. Reproduce with a real Windows account/session before promising persistent owner login. Device-credential persistence passed separately.
- The PDF fixture opened in an isolated session with the bundled viewer initialized. **Its Print control was present and enabled while processing was disabled.** We did not click it or invoke any printing API. Actual spool submission through this control was not tested; the enabled alternative print path must be addressed before claiming all output is approval-controlled.
- Direct `/dashboard/setup` IPC navigation failed, and a normal full-page link to that route was blocked by the Electron navigation policy. SPA navigation is a separate path and was not proven blocked. Restart landed on Welcome and the shell navigation remained Overview / Print jobs / Reports / Printers & setup.
- No job claims, activation requests, real storage access, OS keychain operations, customer documents or physical printing were used. Sanitized runtime results are in [runtime-results.json](runtime-results.json).

Hiding a button alone is insufficient. Do not exercise the path on a connected printer to diagnose it. |
| P0, physical test prerequisite | WindowsVersion requires SumatraPDF >=3.7 and independently verified executable SHA-256. No renderer is included. Official stable download still advertises 3.6.1. A supported, qualified renderer/driver combination is not established. | Qualify an official suitable build and its hash against the exact required flags and pilot printer. Preserve version/integrity checks; do not simply accept 3.6.1 or trust a hash supplied by an unverified download. |
| P0, Windows release gate | DPAPI storage across reboot, installer behavior, printer discovery, PDF preview, renderer behavior and spool/physical outcomes have not been executed on Windows. | Complete the checklist on the actual laptop and printer, with approved test data. Later physical-output steps require separate authorization. |
| P1, owner workflow | Every launch returns to a nine-step installer-style setup flow. Account/shop creation and pricing/QR setup are presented to owners although the operator already did them. Two navigation layers expose overlapping choices. | Default a configured profile to Orders; make only Orders / History / Settings the primary desktop navigation. Keep technician setup under Settings and preserve server authorization. Remove redundant onboarding prompts from the routine owner path. |
| P1, incoming orders | Jobs are server-rendered snapshots; the page explicitly requires Refresh. There is no automatic incoming-order refresh or desktop notification. The 2.5-second shell poll updates local status, not the orders list. | Add bounded, shop-scoped refresh with backoff and a visible updated/offline state. An order must not be approved automatically. Notifications can follow if needed; they are not a prerequisite to a visible queue refresh. |
| P1, session continuity | Synthetic persistent cookie failed the restart test. Owner UI auth is distinct from device identity. Better Auth owner sessions expire after 12 hours with refresh policy; pairing does not authorize owner UI actions. | Investigate using real Windows persistent cookies and controlled login. Keep reauthentication inside Desktop. Do not extend sessions, disable verification or use the device bearer credential as an owner session. |
| P1, recovery workload | Windows adapter never declares physical completion from a spool status alone. Printed/complete flags, disappearing jobs and uncertain submissions need inspection; timeout defaults to five minutes. An unresolved attempt occupies the journal, so subsequent jobs on that device wait. | Make Needs inspection prominent in Orders, with the existing owner-only outcome action. | P1, printer/connection status | Discovery is on demand. The shell reports worker lifecycle, not continuous USB/network/cloud health. Printer heartbeats are emitted by the running worker; stopped processing does not prove the physical printer is disconnected. Devices UI omits current heartbeat/availability details. Offline retry may leave the worker labeled live. | Show separate last-checked cloud, selected Windows queue, device authorization and processing states. | P1, error recovery | Discovery/spooler/version exceptions commonly collapse to a generic setup error. Preview failures send a notice to the local setup page, which is covered by the embedded dashboard. Setup copy says real printing is disabled in this build despite an implemented authorized printing path. | Map safe error codes to driver/PowerShell, renderer/version, paper/offline and cloud/storage guidance. | P1, compatibility | `/dashboard/setup` is absent from both desktop navigation allowlists. All embedded browser downloads are cancelled, including the new QR poster PDF; native QR PNG save is a different supported path. | Explicitly support only the approved setup route and authenticated QR poster download if these belong in Settings. Keep host restrictions and do not enable arbitrary downloads or URLs. Operator can deliver the initial poster through the website meanwhile. |
| P1, device/shop clarity | Embedded owner UI can switch shops while a running worker remains bound to its original paired shop/printer. Agent Start does not reconcile the selected owner-session shop; the optional setup check does. Prevent an operator from mistaking another shop's dashboard for the running queue; do not relax device scope. |
| P1, History | All jobs and per-status views stop at 200 newest records. There is no dedicated historical search/date filter/pagination. | P1 before an extended pilot | Server-issued device credentials expire after 30 days. No renewal path was found. Local summary can still say credential-stored after expiry/revocation until checked. | Show expiry/revocation and an operator-managed re-pair procedure before starting a long pilot. ## Which operations need the website or other tools?

- **Operator before handoff:** account/email verification, creating/selecting the shop, saving rates, initial QR poster and deliberately deciding when customer intake may be enabled. Keep ordering off until explicitly authorized. Registration already creates device-independent shop state; desktop install should not create another shop.
- **Can be inside Desktop today:** owner login and shop selection, order preview/review, approval/rejection, recent history, reports, pricing and Devices & printers. These are embedded website screens; internet/backend access is still required, but an external browser is not inherently necessary.
- **Pairing approval/activation/revocation:** owner-authorized Devices & printers may open inside Desktop. Operator can perform initial approval during handoff. Device pairing never substitutes for owner authentication. Do not share the operator's account with every shop.
- **Currently external or limited:** email verification/recovery links, initial onboarding when direct navigation is blocked, new QR PDF download, installing/configuring the Windows printer driver, qualifying the renderer and OS spool/physical inspection. Native QR PNG save works separately from the PDF poster.
- **Maintenance:** credential expiry/revocation, lost secure storage, replaced Windows profile or renamed/replaced queues need an explicit recovery/re-pair/reselection path. Never copy the encrypted vault to a different Windows user as a provisioning shortcut.

## Proposed minimal navigation

| Primary destination | Purpose | Reuse |
| --- | --- | --- |
| Orders | Default after setup; pending/active jobs, visible connection/printer/processing status, preview, approval/rejection and Needs inspection. Stop remains accessible. | Existing jobs page and authorization/reconciliation APIs; no duplicate printing engine. |
| History | Completed/failed/rejected jobs with paging and filters; Sales/Reports as a section. No automatic reprint. | Existing stored jobs and report calculations, with explicit timezone semantics. |
| Settings | Paired shop/device, printer queue/discovery, renderer, secure connection checks, technician setup, optional Windows startup, Stop and safe Exit. | Existing setup IPC and owner-authorized embedded device/pricing pages. |

This is a proposal only. Keep technician account/shop creation out of everyday navigation. A configured device should open Orders, while Start remains a separate explicit action after each full launch. Do not persist a live-printing intent or silently enable ordering.

## Pilot exit criteria

No customer-facing physical pilot until preview printing is controlled, a qualified renderer/printer is available, real Windows protected storage/restart passes, and the end-to-end approval/uncertainty workflow passes with explicit authorization. A short, attended UI pilot can proceed without claiming these gates are complete. Use [the Windows checklist](windows-test-checklist.md); every checkbox is initially unexecuted.
